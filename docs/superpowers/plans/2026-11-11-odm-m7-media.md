# Milestone 7: HLS/DASH and yt-dlp Backends Implementation Plan

> **Specification Reference:** `docs/superpowers/specs/2026-11-11-odm-design.md` (Sections 2, 3, 4, 5, 6, 12).
> **Milestone Success Criterion:** A stream and a yt-dlp URL download (verified by automated tests across `odm-media`, `odm-core`, `odm-daemon`, `odm-cli`, and `odm-gui`, plus manual checklist `docs/manual-checklists/m7-media.md`).

---

## Architecture and Key Design Decisions

1. **Three backends in one crate (`odm-media`)**:
   - `HlsBackend` — downloads HLS streams by parsing `.m3u8` playlists with `m3u8-rs`, fetching segments via `reqwest` (reusing the same HTTP transfer code pattern from `odm-core::http`), decrypting AES-128 segments when encrypted, concatenating into a `.ts` file, and optionally muxing to `.mp4` with `ffmpeg`.
   - `DashBackend` — downloads DASH streams by parsing `.mpd` manifests with `dash-mpd`, fetching audio and video tracks separately, and muxing with `ffmpeg` (required — DASH jobs fail at probe without `ffmpeg`).
   - `YtDlpBackend` — delegates to the `yt-dlp` external binary. Probe runs `yt-dlp -J <url>` to list formats. Download runs `yt-dlp` as a child process with a progress template and parses stdout into progress events. Pause kills the process; resume reruns with `--continue`. Speed limit is passed via `--limit-rate`.

2. **Backend selection updates (`odm-core::engine`)**:
   - `Source::Url` with a path ending in `.m3u8` → `BackendKind::Hls`.
   - `Source::Url` with a path ending in `.mpd` → `BackendKind::Dash`.
   - For other HTTP URLs: during probe, if the content-type is `application/vnd.apple.mpegurl` or `application/x-mpegURL` → `BackendKind::Hls`; if `application/dash+xml` → `BackendKind::Dash`.
   - If HTTP probe returns `text/html` and yt-dlp is available and finds formats → `BackendKind::YtDlp`.
   - Explicit `backend` override in `JobOptions` allows the client to force a backend.
   - The above is the design spec's selection order (section 2). For M7 the engine only needs static extension-based detection in `add_download`; content-type-based detection happens inside the HLS/DASH probe and is not an engine concern. The yt-dlp fallback detection is a daemon-level concern (the daemon probes HTTP first, then falls back to yt-dlp probe).

3. **HLS encryption (AES-128)**:
   - The `#EXT-X-KEY` tag in HLS playlists specifies `METHOD=AES-128`, a `URI` for the key, and an optional `IV`. The backend fetches the key, constructs the IV (from the tag or from the media sequence number), and decrypts each segment with AES-128-CBC using the `aes` and `cbc` crates.
   - DRM (e.g. `SAMPLE-AES`, Widevine, FairPlay) is detected and fails at probe with a clear message.

4. **Quality/format selection**:
   - HLS master playlists list multiple renditions. `ProbeResult` is extended with `qualities: Option<Vec<QualityInfo>>` to present available renditions (resolution, bandwidth, codecs).
   - DASH manifests list adaptation sets. Same `qualities` field is used.
   - yt-dlp returns formats. Same field is used, mapped from yt-dlp JSON.
   - `JobOptions` gains `quality: Option<String>` — an opaque quality identifier (e.g. resolution string, format ID) that the backend interprets.

5. **ffmpeg dependency**:
   - Found from `Settings::ffmpeg_path`, then from `PATH`.
   - HLS without ffmpeg: keeps the concatenated `.ts` file.
   - DASH without ffmpeg: fails at probe with `"ffmpeg is required for DASH downloads"`.
   - yt-dlp without ffmpeg: yt-dlp handles muxing itself using its own ffmpeg detection, so `odm` does not interfere.

6. **yt-dlp dependency**:
   - Found from `Settings::ytdlp_path`, then from `PATH`.
   - If not found, the `YtDlpBackend::probe` returns an error with a message explaining that yt-dlp is required and where to get it.
   - The daemon does not auto-download yt-dlp; the GUI shows a message with the download link (spec: "clients offer to download it from the official GitHub release into the data folder, after the user confirms").

7. **Pause/resume for each backend**:
   - **HLS/DASH:** Backend tracks which segments have been downloaded in `backend_state` JSON. On pause, saves the list of completed segment indices. On resume, skips completed segments.
   - **yt-dlp:** Pause sends SIGTERM (Unix) / `taskkill` (Windows) to the child process. Resume reruns `yt-dlp --continue` which picks up from partial files.

8. **Progress reporting**:
   - **HLS:** Progress = (segments_downloaded / total_segments) × estimated_total_bytes. Since individual segment sizes aren't known upfront, the backend reports downloaded bytes accurately and total bytes as an estimate after the first segment.
   - **DASH:** Similar to HLS but audio and video tracks report separately; combined bytes are reported.
   - **yt-dlp:** Parsed from yt-dlp's stdout progress template: `%(progress._percent_str)s %(progress._total_bytes_str)s %(progress._speed_str)s`.

9. **Settings**:
   - New settings: `ffmpeg_path` (default `""`), `ytdlp_path` (default `""`).
   - Exposed through `GET/PATCH /api/v1/settings`.

10. **Resume state persistence**:
    - HLS/DASH store `{ "completed_segments": [0, 1, 2, ...], "selected_quality": "720p" }` in `backend_state`.
    - yt-dlp stores `{ "format_id": "22", "output_template": "..." }` in `backend_state`. yt-dlp's own partial files handle the actual byte-level resume.

### Task 3: HLS Backend (`odm-media`)

**Files:**

**Interfaces:**
- Produces: `HlsBackend` implementing `Backend`.
- `HlsBackend::new(http_client: reqwest::Client, ffmpeg_path: Option<PathBuf>) -> Self`.
- `probe`: fetches the `.m3u8` URL, parses with `m3u8-rs`. If it's a master playlist, returns `QualityInfo` for each variant. - AES-128 decryption: when `#EXT-X-KEY METHOD=AES-128` is present, fetches the key from the URI, uses the IV from the tag (or derives from media sequence number), decrypts each segment after download.

- [x] **Step 2: Implement HlsBackend**

In `crates/odm-media/src/hls.rs`:
```rust
#![forbid(unsafe_code)]

use std::path::{Path, PathBuf};
use std::sync::Arc;

use async_trait::async_trait;
use m3u8_rs::{MediaPlaylist, MasterPlaylist, Playlist};
use odm_core::backend::{Backend, BackendError, JobContext, RunOutcome};
use odm_core::job::{BackendKind, JobOptions, ProbeResult, Source};
use reqwest::Client;
use url::Url;

use crate::mux;
use crate::quality::QualityInfo;
use crate::state::HlsResumeState;

pub struct HlsBackend {
    client: Client,
    ffmpeg_path: Option<PathBuf>,
}
```

Key implementation details:
- `probe`:
  1. Fetch the URL with `reqwest`.
  2. Parse bytes with `m3u8_rs::parse_playlist(&bytes)`.
  3. If `Playlist::MasterPlaylist(master)`: extract variants into `QualityInfo` list (resolution from `RESOLUTION`, bandwidth from `BANDWIDTH`, codecs from `CODECS`). Return `ProbeResult` with qualities.
  4. If `Playlist::MediaPlaylist(media)`: count segments, check for `#EXT-X-KEY`. If DRM detected, return error. Estimate total size = segment count × first segment size (or 0 if unknown). Derive filename from the URL path.
  5. Check for `Source::Url(_)` only; return `BackendError::Unsupported` for non-URL sources.

- `run`:
  1. Resolve the quality: if `JobOptions::quality` is set, find the matching variant in the master playlist and use its URI; otherwise use the first/best variant.
  2. Fetch the media playlist.
  3. Load `HlsResumeState` from `ctx.job.backend_state()` if resuming.
  4. For each segment in the playlist:
     - Check `ctx.control` for pause/cancel before each segment.
     - Skip segments already in `completed_segments`.
     - Fetch the segment bytes with `reqwest`.
     - If AES-128 encrypted: fetch the key (cache it — typically one key per playlist), construct IV, decrypt with `aes`/`cbc`.
     - Append to the output `.ts` file.
     - Report progress via `ctx.progress.report(...)`.
     - Record the segment index in `completed_segments`.
     - Save `HlsResumeState` to `ctx.store.set_backend_state(...)` periodically (every 5 segments or on pause).
  5. After all segments: if `ffmpeg_path` is `Some` and ffmpeg exists, mux `.ts` → `.mp4` and delete the `.ts` file. Otherwise keep the `.ts` file.
  6. Rename to final filename and return `RunOutcome::Completed`.

fn decrypt_segment(data: &[u8], key: &[u8; 16], iv: &[u8; 16]) -> Result<Vec<u8>, BackendError> {

}
